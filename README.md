# Что готовить — рецепты с подбором по холодильнику

Веб-приложение с каталогом рецептов и «умным холодильником»: пользователь
отмечает продукты, которые есть дома, и получает список блюд, которые можно
приготовить из них. Фронтенд — Vue 3 SPA с 3D-кухней на three.js, бэкенд —
Laravel 12 + Sanctum (токеновая авторизация).

---

## Стек

| Слой | Технологии |
|------|-----------|
| Бэкенд | Laravel 12, PHP 8.3, Sanctum, Eloquent, MySQL |
| Фронтенд | Vue 3, Pinia, vue-router, @unhead/vue, Vite, three.js |
| Сборка фронта | `frontend/` → `public/frontend` (манифест читает `resources/views/spa.blade.php`) |
| Тесты | PHPUnit, `RefreshDatabase`, sqlite `:memory:` |

## Установка

```bash
composer install
npm --prefix frontend install

cp .env.example .env
php artisan key:generate
```

В `.env` укажите подключение к базе и заполните два обязательных значения:

```dotenv
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_DATABASE=what_to_cook
DB_USERNAME=root
DB_PASSWORD=

# Администратор, которого создаёт сидер.
# Без этих переменных сидер ничего не делает — пароль по умолчанию
# был бы одинаковым на всех установках.
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=ваш-пароль
```

Затем миграции, наполнение данными и сборка фронтенда:

```bash
php artisan migrate
php artisan db:seed          # категории, ~1000 рецептов, шаги, фото, ингредиенты, админ
php artisan storage:link     # символическая ссылка public/storage -> storage/app/public
npm --prefix frontend run build
php artisan serve
```

> `public/storage` — служебная ссылка, она **не коммитится** (проверьте
> `.gitignore`). Создаётся только через `php artisan storage:link`.
> Без неё загруженные и импортированные изображения не отдаются по `/storage/...`.

`php artisan db:seed` идемпотентен: повторный запуск не создаёт дубликатов.
`WebRecipeSeeder` обновляет существующие записи на месте, `ImageUrlSeeder`
подставляет настоящие фотографии блюд (см. раздел «Фотографии»), а
`AdminUserSeeder` создаёт администратора (или обновляет пароль существующего).

## Авторизация

Токены Sanctum, передаются в заголовке `Authorization: Bearer <token>`.

```bash
# Регистрация → 201 { message, data, token }
curl -X POST http://127.0.0.1:8000/api/auth/register \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"name":"Иван","email":"ivan@example.com","password":"secret123","password_confirmation":"secret123"}'

# Вход → 200 { message, data, token }
curl -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"email":"ivan@example.com","password":"secret123"}'

# Кто я
curl http://127.0.0.1:8000/api/auth/me -H 'Authorization: Bearer <token>'

# Выход — токен отзывается
curl -X POST http://127.0.0.1:8000/api/auth/logout -H 'Authorization: Bearer <token>'
```

При неверном логине и неизвестном e-mail текст ошибки одинаковый, чтобы по
форме входа нельзя было выяснить, какие адреса зарегистрированы.

### Смена и восстановление пароля

```bash
# Смена пароля (нужен токен). Остальные токены пользователя отзываются.
curl -X POST http://127.0.0.1:8000/api/auth/password \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"current_password":"secret123","password":"newsecret123","password_confirmation":"newsecret123"}'

# Запрос ссылки для сброса. Ответ одинаков для существующих и несуществующих адресов.
curl -X POST http://127.0.0.1:8000/api/auth/forgot-password \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"email":"ivan@example.com"}'

# Сброс по токену из ссылки
curl -X POST http://127.0.0.1:8000/api/auth/reset-password \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"token":"<из ссылки>","email":"ivan@example.com","password":"newsecret123","password_confirmation":"newsecret123"}'
```

Письмо со ссылкой уходит через `MAIL_MAILER` из `.env`; по умолчанию там
`log`, то есть ссылка печатается в `storage/logs/laravel.log`. В локальной
среде (`APP_ENV=local`) ссылка дополнительно приходит в ответе
`POST /api/auth/forgot-password` полем `data.reset_url` — иначе на dev-стенде
без почты восстановить пароль было бы нечем. В продакшене это поле не
возвращается.

### Права администратора

`POST /api/upload/image` доступен только администратору (`is_admin = true`).
Обычный пользователь получает 403, анонимный — 401.

Учётная запись администратора создаётся сидером из переменных `ADMIN_EMAIL`
и `ADMIN_PASSWORD` в `.env`. Отдельной админки в интерфейсе нет — это
обычный вход на http://127.0.0.1:8000/login, но с доступом к закрытым
маршрутам. Локальная памятка с логином, паролем и командами запуска лежит
в `ADMIN.md` (файл с паролем не коммитится — он в `.gitignore`).

| GET | `/api/recipes/{slug}/comments` | комментарии к рецепту (публично) |

Фильтры каталога: `category_id` (или `category` — slug'ом), `difficulty`
(`easy`/`medium`/`hard`, можно через запятую), `max_time`, `sort`

Неизвестное значение `difficulty` игнорируется, а не обнуляет выдачу.

### Подбор по холодильнику

`POST /api/fridge/match` принимает:

- `ingredients` — список продуктов (обязательно);
- `include_pantry_staples` — считать ли базовые продукты недостающими,
  по умолчанию `false`;
- `min_match` — минимальный процент совпадения, по умолчанию **70**.

Рецепты с совпадением ниже порога в выдачу не попадают: «почти готово» —
это когда не хватает пары продуктов, а не когда совпало одно слово из
десяти. Порог можно ослабить до `0` — тогда вернутся все рецепты, где
нашёлся хотя бы один продукт.

Каждый рецепт в ответе содержит `match_percentage` (целое число),
`matched_count` и `total_count` (сколько продуктов нашлось и сколько
нужно всего), `matched_ingredients`, `missing_ingredients` (массив
объектов `{name, quantity}`) и `ignored_pantry_staples`. Выдача отсортирована
по совпадению — сначала лучшие.

В интерфейсе фильтры применяются сразу, как только пользователь изменил
сложность, время приготовления, категорию или сортировку — кнопка
«Применить фильтры» больше не обязательна. Применённые фильтры показаны
«чипсами» над списком, каждый снимается одним кликом, и снятый фильтр сразу
убирается из адреса страницы, чтобы ссылкой можно было поделиться.

Любой неизвестный путь внутри `/api` возвращает JSON `404` — и для `GET`,
и для остальных методов.

### Персональные данные на публичных маршрутах

Каталог, карточка рецепта и список комментариев открыты для гостей, но если
запрос пришёл с токеном, сервер узнаёт пользователя и добавляет личные поля:

- `is_favorite` — отметка «в избранном» у рецепта;
- `can_delete` — может ли текущий пользователь удалить комментарий
  или фотоотчёт.

Это работает через middleware `auth.optional`: обычный `auth:sanctum` на
публичном маршруте отклонил бы гостя, а без него пользователь не определялся
вовсе. Такие поля считаются отдельно от кеша карточки — кеш общий для всех,
а избранное личное.

### Фотоотчёты

Под каждым рецептом — фотографии, которые прислали те, кто его приготовил.
Загрузить фотоотчёт может и гость, под своим именем; имя гостю обязательно
(как и в комментариях).

Файл проверяется на стороне Laravel и довольно строго:

- только настоящие изображения — jpeg, png, webp, до 5 МБ;
- MIME-тип определяется **по содержимому** файла, а не по расширению и не по
  типу, присланному клиентом: переименованный код с картинкой внутри
  отклоняется;
- имя файла — UUID, расширение — из определённого сервером MIME-типа, а не
  из имени, которое прислал браузер.

Файлы лежат в `storage/app/public/results` и отдаются через
`/storage/results/...` (нужна ссылка `public/storage`, см. «Установка»).
Удалить фотоотчёт может автор или администратор — `App\Policies\RecipeResultPolicy`.
Гостю доступно 3 фотоотчёта за 15 минут с одного адреса (лимит `guest-result`).

### Комментарии гостей

Написать комментарий может и гость — под именем. Имя хранится рядом с
комментарием (`comments.guest_name`), а `user_id` остаётся пустым, так
что аккаунт заводить не нужно.

Гостю имя обязательно: без него комментарий остался бы анонимным, и
удалить его не смог бы никто, включая автора. Удалить комментарий может
только его автор или администратор — это проверяет
`App\Policies\CommentPolicy`. Гостю кнопка удаления не показывается.

С гостя спрашивают строго: 3 комментария за 15 минут с одного адреса
(лимит `guest-comment`). Авторизованных этот лимит не касается.

### Базовые продукты

Соль, перец, масло, сахар, мука и вода есть в любой кухне. Требовать
отметить их в холодильнике — значит занижать совпадение у всех рецептов
подряд, поэтому такие продукты помечены в справочнике флагом
`is_pantry_staple` и по умолчанию выпадают из расчёта.

Флаг ставит сидер продуктов (`IngredientSeeder`), а правила отбора лежат
в `App\Services\PantryStaples`. Сравнение идёт по названию целиком, а не
«по слову»: «Перец болгарский» и «Сахарный горошек» — это овощи, «Маслины» —
оливки, а «Соль, перец, масло» — перечисление из текста рецепта, а не один
продукт. Ни один из них базовым не считается.

`POST /api/fridge/match` принимает необязательный `include_pantry_staples`
(по умолчанию `false`). Если флаг включён, базовые продукты считаются
недостающими наравне с остальными, иначе они просто не учитываются, а в
ответе приходят в поле `ignored_pantry_staples`.

## Ограничения частоты запросов

Лимиты заданы в `AppServiceProvider::registerRateLimiters()` и подключены
к маршрутам через `throttle:<лимит>`. Каждый лимит двойной: считается и по
пользователю, и по IP-адресу. Лимит только по пользователю обходится
регистрацией десятка аккаунтов, лимит только по IP — сменой адреса; запрос
проходит, только если не исчерпан ни один из счётчиков.

| Лимит | На пользователя (или гостя с одного IP) | На один IP обобщённо | Куда применяется |
|-------|------------------------------------------|------------------------|-------------------|
| `api-read` | 120/мин | 400/мин | каталог, категории, ингредиенты, избранное |
| `api-detail` | 240/мин | 800/мин | карточка рецепта |
| `api-search` | 60/мин | 200/мин | поиск и подбор по холодильнику |
| `api-write` | 20/мин | 60/мин | загрузка изображений, избранное, комментарии, смена пароля |
| `api-login` | 10/мин | 10/мин | вход |
| `api-register` | 5/мин | 20/мин | регистрация |
| `api-reset` | 5/мин | 20/мин | сброс пароля |
| `guest-comment` | 3/15 мин | — | комментарии гостей (счёт по IP) |
| `guest-result` | 3/15 мин | — | фотоотчёты гостей (счёт по IP) |

Лимиты `guest-comment` и `guest-result` устроены особо: они считают только
гостей и работают по IP. Авторизованных они не касаются — у них общий лимит
`api-write`. Проверка идёт по токену, а не по `$request->user()`: middleware
ограничения частоты в Laravel выполняются раньше middleware авторизации,
и на момент проверки пользователь ещё не определён.


## Язык

В `.env` выставлен `APP_LOCALE=ru`, поэтому сообщения валидации и письмо о
сбросе пароля приходят по-русски. Переводы лежат в `lang/ru/`
(`validation.php`, `auth.php`, `passwords.php`) и в `lang/ru.json` — там
живут строки стандартного уведомления Laravel о сбросе пароля, ключи которых
равны английскому тексту.

Правил, для которых нет перевода, не страшно: Laravel подставит английский
fallback (`APP_FALLBACK_LOCALE=en`).

## Кеш

Карточка рецепта кешируется на 10 минут. Ключи кеша сбрасываются при
сохранении и удалении рецепта (`Recipe::booted()`), поэтому правка рецепта
видна сразу, а не по истечении TTL. Счётчик просмотров в кеш не попадает —
он читается из базы при каждом запросе.

`php artisan db:seed` в конце делает `Cache::flush()`: сидеры пишут данные
напрямую и обходят события модели, поэтому кеш иначе остался бы со старыми
карточками.

## PWA (установка и работа без сети)

Приложение можно поставить на телефон как отдельное приложение и открывать
без интернета. Service worker и манифест собирает `vite-plugin-pwa`
(`generateSW`), манифест написан руками — `public/manifest.webmanifest`.

| Файл | Что это |
|------|---------|
| `public/manifest.webmanifest` | имя, иконки, цвета, `start_url`, `display: standalone` |
| `public/sw.js` | сгенерированный service worker, лежит в корне сайта |
| `public/img/icon-192.png`, `icon-512.png`, `icon-maskable-512.png` | иконки приложения |
| `frontend/vite.config.js` | настройки `VitePWA`: что попадает в precache и в runtime-кэш |

Service worker лежит в **корне** сайта (`/sw.js`), а не в `/frontend/`: у
service worker'а scope определяется его расположением, и из `/frontend/`
он не контролировал бы страницы рецептов. Поэтому в precache попадают
`frontend/index.html` (оболочка) и файлы сборки, а `navigateFallback`
отдаёт оболочку для любого маршрута SPA.

Оболочка одна и та же для сервера и для офлайна: `resources/views/spa.blade.php`
отдаёт собранный `public/frontend/index.html` как есть, а service worker
кладёт в кеш ровно этот файл. Благодаря этому страница выглядит одинаково
онлайн и офлайн, а обновления подхватываются сами: workbox пересчитывает
ревизии файлов при каждой сборке, `skipWaiting` и `clientsClaim` включены,
`registerType: 'autoUpdate'`.

Что работает без сети:

- страницы приложения и каталог рецептов — из precache;
- ответы API — `NetworkFirst` (сеть, при её отсутствии кеш, таймаут 3 с);
- картинки блюд и фотоотчётов — `CacheFirst`.

Что намеренно не кешируется: `/api/auth` (вход и токены) и `/api/favorites`
(личное состояние пользователя).

Регистрация service worker'а — только в продакшен-сборке (`import.meta.env.PROD`),
чтобы не мешать разработке. После изменения фронтенда нужна пересборка:

```bash
cd frontend && npm run build
```

Он заново создаст `public/sw.js` и обновит precache.

## Фотографии

Раньше у рецептов из локального каталога не было своих фотографий, и
`ImageUrlSeeder` подставлял случайные картинки с picsum.photos — в каталоге
«Яичница праздничная» показывалась фотография машины. Теперь у каждого
блюда есть настоящее фото:

| Что | Откуда | Где лежит |
|-----|--------|-----------|
| Фото блюда из локального каталога | TheMealDB (793 блюда) | `database/seeders/data/dish_photos.json` |
| Запасные фото по категориям | TheMealDB | там же, ключ `pools` |
| Фото рецептов из интернета | TheMealDB и Food.com | `database/seeders/data/web_recipes.json` (генерируется скриптом) |
| Фото шагов приготовления | Food.com (снимки процесса) | `database/seeders/data/foodcom_images.json` |
| Фото категорий | Unsplash | константа `CATEGORY_IMAGES` в `ImageUrlSeeder` |

Блюдо опознаётся по названию: «Яичница праздничная» находит «Яичницу»,
«Плов с курицей» — «Плов с курицей», а не более короткий «Плов». Если
название не опознано, берётся фото из пула категории.

Ссылки на picsum.photos и loremflickr считаются заглушками: сидер
заменяет их настоящими фотографиями. Шаг без настоящего фото остаётся
без картинки — фотография машины вместо снимка процесса хуже, чем просто
шаг текстом.

Файлы `dish_photos.json` и `foodcom_images.json` лежат в репозитории, так
что сидер работает без доступа в интернет. Обновить их можно скриптом
`node database/seeders/data/fetch_web_recipes.mjs` — он заново скачает
рецепты и перезапишет фотографии шагов.

## Интерфейс

SPA собрана из страниц:

| Путь | Что делает |
|------|-----------|
| `/` | главная |
| `/recipes` | каталог с фильтрами |
| `/recipes/:slug` | карточка рецепта с избранным и комментариями |
| `/categories`, `/categories/:slug` | категории |
| `/search` | поиск |
| `/fridge` | 3D-кухня с холодильником и подбором |
| `/random` | случайный рецепт |
| `/login` | вход, регистрация и «забыли пароль» (три режима на одной странице) |
| `/reset-password` | установка нового пароля по ссылке из письма |
| `/favorites` | избранное (только для авторизованных) |
| `/account` | профиль, смена пароля, выход (только для авторизованных) |

Токен Sanctum лежит в `localStorage` (`auth-token`), профиль — в `auth-user`.
Все запросы идут через общий axios-инстанс `frontend/src/api.js`, который сам
подставляет заголовок `Authorization` и убирает сессию, если сервер ответил
401 (токен протух или отозван).

Избранное у гостя хранится локально в `localStorage` (`fav-slugs`) и после
входа сливается на сервер — так ранее отмеченные рецепты не теряются.

## Структура

```
app/
  Http/Controllers/Api/    контроллеры API
  Http/Middleware/         EnsureUserIsAdmin, AuthenticateIfPresent
  Models/                  Recipe, Category, Ingredient, User, Favorite, Comment, RecipeResult
  Services/FridgeMatcher   подбор рецептов по продуктам
  Support/Slug             транслитерация slug'ов
  Support/Utf8             чистка текста, пришедшего от клиента
database/
  migrations/              схема
  seeders/                 наполнение данными
lang/ru/                   переводы сообщений валидации и писем
frontend/
  src/api.js               axios-инстанс: токен, 401-обработчик
  src/views/               страницы SPA
  src/components/          карточка, фильтры, шаги, 3D-кухня, избранное, комментарии, фотоотчёты
  src/stores/              Pinia: recipes, fridge, auth, favorites
  vite.config.js           сборка + настройки PWA (precache, runtime-кэш)
public/
  manifest.webmanifest     манифест PWA
  sw.js                    service worker (генерируется при сборке)
  img/                     иконки приложения
resources/views/spa.blade.php   оболочка SPA
routes/api.php             маршруты API
routes/web.php             SPA-fallback
```

## Тесты

```bash
php artisan test
```

Покрыты: аутентификация и отзыв токена, права администратора на загрузку,
лимиты частоты запросов, JSON-ответы для неизвестных путей `/api`, фильтр
`difficulty`, инвалидация кеша карточки и рост счётчика просмотров, сидеры
(веб-рецепты, изображения), избранное (в том числе личность `is_favorite` на
публичных маршрутах), комментарии, фотоотчёты (в том числе проверка типа
загружаемого файла по содержимому и лимит гостей), смена пароля и сброс
пароля, PWA (манифест, иконки, service worker в корне сайта, оболочка с
ссылкой на манифест), русские сообщения валидации.

## Что стоит сделать следующим

- Подтверждение email при регистрации и письма о новых комментариях.
- Аватар и редактирование профиля.
- Поиск по ингредиентам в «холодильнике» без ручного отбора продуктов.
- Полноценные картинки пользовательских рецептов (сейчас загрузка есть
  только у администратора).
- CI: прогон `php artisan test` и сборка фронтенда на каждый коммит.
